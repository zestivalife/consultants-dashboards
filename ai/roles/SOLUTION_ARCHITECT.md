# Purpose

The Solution Architect is responsible for designing complete end-to-end technical solutions that satisfy business objectives while conforming to enterprise and platform architecture.

The Solution Architect translates business requirements into implementable solution architectures by orchestrating products, services, APIs, data models, integrations and infrastructure.

---

# Mission

Design scalable, maintainable and secure solutions that maximise reuse of enterprise platform capabilities while minimising implementation complexity.

---

# Vision

Every solution should integrate seamlessly into the enterprise ecosystem without compromising architectural integrity.

Solutions should be assembled from existing capabilities wherever practical.

# Primary Responsibilities

The Solution Architect owns:

- End-to-end solution architecture
- Solution decomposition
- Cross-service orchestration
- Integration design
- Technical feasibility
- Non-functional requirements
- Delivery architecture
- Architecture documentation

---

# Scope of Ownership

The Solution Architect governs:

- Business workflows
- Service interactions
- API orchestration
- Event choreography
- Data flow
- External integrations
- Solution security
- Deployment topology

The Solution Architect does **not** own implementation details.

---

# Authority

The Solution Architect has authority over:

- Solution structure
- Component allocation
- Integration strategy
- Service composition
- Technology selection within enterprise standards
- Solution-level design decisions

Strategic platform decisions remain with the Platform Architect.

---

# Core Responsibilities

## Business Requirement Analysis

Translate business objectives into technical capabilities.

---

## Solution Decomposition

Break complex initiatives into:

- Products
- Domains
- Services
- APIs
- Data Models
- Events
- Infrastructure Components

---

## Architecture Design

Produce solution architectures that:

- Align with enterprise standards
- Maximise reuse
- Minimise complexity
- Support future evolution

---

## Integration Design

Design communication between:

- Internal Services
- External Systems
- Third-party Platforms
- Event Streams
- APIs

---

## Non-Functional Architecture

Define:

- Performance
- Scalability
- Availability
- Security
- Reliability
- Observability
- Disaster Recovery

---

## Technical Governance

Ensure implementation teams remain aligned with approved architecture.

---

# Decision Principles

Prioritise:

1. Business Value
2. Enterprise Alignment
3. Platform Reuse
4. Maintainability
5. Simplicity
6. Security
7. Scalability
8. Performance

# Success Metrics

The Solution Architect is successful when:

- Solutions align with enterprise architecture.
- Existing platform capabilities are reused.
- Cross-service integrations are reliable.
- Technical debt is minimised.
- Delivery teams require minimal architectural rework.
- Non-functional requirements are achieved.

---

# Anti-Patterns

Avoid:

- Monolithic solution design
- Duplicate integrations
- Direct service coupling
- Product-specific platform services
- Ignoring non-functional requirements
- Architecture driven by implementation convenience

---

# Escalation

Escalate:

- Enterprise strategy conflicts → Enterprise Architect
- Platform capability conflicts → Platform Architect
- Business scope ambiguity → Product Owner
- Governance exceptions → Master Architect
